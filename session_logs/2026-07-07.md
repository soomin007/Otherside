## 세션 1 (폭풍 3층 시각 연출 배선 — StormFX + 1층 헤이즈)

### 요약
폭풍 biome 단면 화면에 시각 폭풍이 전혀 없던 것을 해결(소리만 났음). 세션 20의 탐색 화면
풀스크린 재구성 때 옛 1층 그라데이션 띠(`Expedition._draw_storm`)가 사라졌고, 완성돼 있던
`StormFX`(2·3층 파티클)는 어디에도 인스턴스화되지 않은 채였다. 폭풍 노드(c2 모래의 벽·f1 폭풍의 문)
도착 시 3층을 얹도록 배선하고, 밝은 폭풍 아트 위에서 파티클이 안 보이던 대비 문제(세션 7 교훈)를 톤 조정으로 해결.

### 주요 변경
- `scripts/ui/Expedition.gd` — 폭풍 biome 분기(`play_storm` 옆)에서 `_spawn_storm_fx()`:
  `StormFX` 인스턴스를 첫 자식(단면 그림 위·HUD/모달 아래)으로 얹음. `_draw` 에 1층 옅은 모래
  헤이즈(`_make_storm_haze`, 위 짙고 아래 옅은 따뜻한 베일) + 매 프레임 화면 전체로 `set_band`(리사이즈 추종).
  헤더 주석·멤버(`_storm_fx`/`_storm_haze`) 갱신.
- `scripts/ui/StormFX.gd` — 입자 색을 배경보다 밝은 톤으로 분리(세션 7: 배경색과 같으면 대비 0):
  중경 = 발광 먼지(`HAZE` 0.90/0.84/0.70, α0.15), 전경 = 빛나는 모래(`LIT` 0.96/0.92/0.80, α0.55, 수 30→38).
  안 쓰던 `SAND` 상수 제거(외부 참조 없음 확인 — `make_dot_texture`는 Map 드리프트가 계속 공유).
- 문서: `backlog.md`·`00_START_HERE.md` §10 — "폭풍 파티클 3층" 항목을 "배선 완료, 실기기 성능·감각 확인만"으로 갱신.

### 결정 사항
- **1층 = _draw 헤이즈, 2·3층 = StormFX 파티클.** 옛 1층 띠가 풀스크린 재구성으로 사라졌으므로 1층을
  풀스크린 헤이즈로 되살려 기획서 §5의 "3층 경량화"를 완성. 전부 웹 안전(draw + CPUParticles2D, 셰이더/GPUParticles 없음).
- **입자는 밝게(빛 받은 모래).** 밝은 폭풍 아트 위에선 대비가 낮아 어두운 영역(전경·하단)에서 주로 읽히고,
  밝은 벽 위에선 은은하다 — 정지컷에선 미묘하나 실기기 움직임이 마저 살린다(과증폭 = 점박이 폭풍 회피).
- 파티클을 첫 자식으로 둬 HUD·버튼·모달·붓글씨 지명이 항상 그 위에서 읽히게(가독 우선).

### 검증
- `--headless --import` = 전 스크립트 파싱 0 에러. 창모드 스크린샷 드라이버(폭풍 노드 f1 강제 도착,
  세이브 무영향, 확인 후 삭제)로 3층 렌더 확인 — 헤이즈·중경·전경 모두 그려지고 UI 가독 유지, 튜닝 전/후 대비 개선 확인.

### 미해결 / 다음
- 실기기(폰/데스크톱 웹) 성능·감각 확인: 파티클 밀도·움직임 속도, 밝은 배경 대비 체감.

### 요약
사용자 요청 2건. ① 이동 중 폭풍 위협 상황 카드(Map 화면)에도 폭풍 3층을 얹어 도착 단면과 통일.

### 주요 변경

  어둠(dim) 위·내용(center) 아래에 StormFX(2·3층) + 헤이즈(1층)를 끼워 폭풍이 카드 뒤에서 몰아치게 함.
  카드 닫힘·리사이즈 처리(`_on_situation_choice`·`_layout_chrome`). Expedition 단면과 같은 StormFX 공유.
- `scripts/ui/DebugOverlay.gd` — `_on_jump_selected`: `go_to_map` → `begin_edge(target)` +
  즉시 도착(`_edge_step = _edge_len`) + `go_to_expedition`. 드롭다운 라벨 "노드 단면으로 점프…".
  end 노드면 Expedition 이 엔딩을 띄운다(부수 이득).
- 문서: `backlog.md` 폭풍 항목의 "이동 중 카드 후보"를 완료로 갱신.

### 결정 사항
- **폭풍 카드는 어두운 scrim 위** — 밝은 폭풍 아트 위(Expedition)보다 오히려 밝은 모래 입자 대비가 잘 산다.
  같은 StormFX·헤이즈를 재사용(중복 로직 회피), 폭풍 위협 카드일 때만 켜고 닫힘에 분출 정지.
- **디버그 점프 = 도착 상태로.** `begin_edge` 로 엣지를 걸고 걸음을 건너뛰어 즉시 도착 처리 →
  `target_node_id()`=목표, 단면이 뜬다. 돌아가기(`arrive_node`)가 엣지를 정상적으로 닫아 dangling 없음.

### 검증

## 세션 3 (웹 메모리 다이어트 조사 — "1GB" 진단)

### 요약
"웹에서 1GB 먹는다"는 우려를 실측으로 진단. 결론: **대체로 Godot 4 웹 export 자체의 엔진 베이스라인**
(wasm 36MB + 엔진 힙 + 브라우저)이고 우리 에셋은 이미 상당히 최적화 상태. 안전한 유일 이득이던
미참조 root 원본 30장 제외를 실행(pck 50→48MB). 폰트·BGM은 조사 결과 안전하게 줄일 수 없음을 확인.

### 주요 변경
- 미참조 root 원본 아트 30장(png+import)을 `assets/arts/` → `assets_src/arts_originals/`(.gdignore) 이동.
  transparent/ 컷아웃 트윈이 있고 경로·uid 모두 런타임 미참조 확인. pck 50.0→48.0MB, 디스크 소스 20.4MB 정리.
- `fonttools` 로컬 설치(폰트 분석용).

### 결정 사항
- **폰트 서브셋 포기.** MaruBuri(7.7MB)·나눔붓(3.4MB)은 한자·가나·키릴 0개(=제거할 게 없음),
  7.7MB의 정체는 한글 음절 11,172자 그 자체. "쓰는 글자만" 서브셋은 `Loadout` 이름 LineEdit(자유 입력)
  때문에 두부(□) 위험 → 큰 폰트는 안전하게 못 줄임. (내가 "폰트부터"라 추천했으나 조사 후 철회.)
- **BGM 재인코딩 포기.** 이미 77~92kbps(스킬 목표 96kbps 밑). 13MB는 총 21분 길이 탓 → 못 줄임.
- **아트 lossy는 이미 완료**(89장 중 65장 mode=1). 무손실 24장은 전부 아이콘·소형 낙서 → 올바르게 유지.
- **다이어트 헤드룸은 거의 소진.** pck 48MB 중 폰트 11 / BGM 13 / SFX 2.8 은 손 못 댐. 아트는 lazy load
  라 동시 VRAM은 이론상 최대(transparent 30장 44MB)보다 훨씬 작음 → 다운스케일 실이득도 작음.

### 미해결 / 다음
- **실측이 최우선.** "1GB"는 미검증 전언. 브라우저(특히 폰)에서 실제 탭 메모리를 재서 iOS Safari
  ~1~1.5GB 강제종료 임계에 실제로 근접하는지 확인해야 판단 가능(헤드리스로는 불가).
- 실측이 위험권이면 남은 유일한 큰 레버 = **ETC2 VRAM 압축**(`for_mobile=true`). WebGL2 코어 지원이라
  전 브라우저 동작하나 텍스처가 lossy(부드러운 알파 가장자리·그라데이션에 블록 아티팩트 위험) → 시각 검증 필수.

### 후속 (누수 조사 결론)
- **메모리 누수 없음 확정.** `Transition.go`가 `get_tree().change_scene_to_file`로 씬을 통째 교체 →
  이전 화면 노드·텍스처가 매 전환마다 해제. 화면을 넘어 사는 건 `Figures._tex_cache`(정적, 초상 3종, 수 MB)뿐,
  Map 아이콘·SectionArt·Opening 삽화 캐시는 인스턴스라 씬과 함께 해제. 원정 반복해도 안 쌓임 = **평평한 천장**.
- 함의: 폰은 "서서히 죽는" 게 아니라 초반에 최고점을 찍는 구조 → 뜨고 두 단계 굴러가면 이미 메모리 통과.
- 사용자 결정(2026-07-07): 브라우저 실측 대신 **Pages 빌드 폰 실플레이로 감수**. 에셋 다이어트는 여기서 닫음
  (더 깎아야 1GB 중 ~20MB, 헛수고). 폰에서 실제 리로드/Aw-Snap 나면 그때 ETC2 착수.

- **추가 지점은 순자원 ≤0(교환·위험·투자·정서).** 기존 자원 캐시(생명선)는 그대로 두어 "최선 2개"의
  자원 합을 보존 → 예산 2에서 economy 불변. 늘어난 건 **선택지 수와 변주**(TWoM식 하드 트레이드오프).
- **디버깅 과정:** 처음엔 공짜 자원 지점을 섞어 end 도달 43%로 폭등 → 순자원 ≤0으로 재설계해 8.0% 복귀.
  그 전 0.0% 폭락은 시뮬이 이벤트를 무조건 먼저 파던 모델 한계 → `_spot_value` 주요/보조 구분으로 해결.
- 부수효과: 사인이 갈증 62%→48%·배고픔 29%→44%로 더 균형(물↔식량 교환 지점 덕, backlog "갈증/배고픔 비율" 항목에 부합).
- 자기비동기 플래그는 **기존 소비처 있는 것만** 재사용(dangling 방지): oasis_widened·camp_shelter·bones_mourned·pool_drank·water_stocked.
